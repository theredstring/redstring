### The trace
In the page, the helper imports `/src/store/canvasUIStore.js` (the app's own module instance, as `helpers.js` does) and
takes a snapshot **synchronously on every canvasUIStore change** and **once per `requestAnimationFrame`**. Consecutive
identical snapshots are collapsed; there are no timestamps. `stop()` returns the distinct sequence (the `all`
stream). Ids created during a scenario would be renamed `new:1…`; none of the 17 scenarios produces one in a recorded
field.

## Determinism

- The `all` stream is deterministic **provided each step settles first** (`waitForQuiet`: no new snapshot for 500 ms).
  The 16 original scenarios were recorded **5 times** (worker counts 2, 3, 4 and default; three scratch runs, the
  committed baseline, and a verify run) and were byte-identical every time; `F6_secondClick` 4 times, identical.
  Final check: record into `lifecycle-baselines/`, re-record into a temp dir with 4 workers, `diff -r` → identical.
- The `F33`–`F37` flows passed 3× with `--repeat-each 3` (33/33), and once more in the combined run.
- **The frame-only stream is NOT deterministic**, even after keeping only states that held for ≥2 consecutive
  frames (`stop({ source: 'frame' })` does that). Where independent timers end within a frame or two of each other,
  a short state is painted for 1–3 frames depending on the run. Seen in F9, F31, F34_cancelBack, F35_clickAway,
  F35_stage2Escape: always the carousel-exit tail — `{ exit guard lowered (300 ms timer), abstraction panel exiting
  (its fly-out), pie popping (340 ms for 8 bubbles) }`. The raw per-frame stream was worse (a "store has pie data,
  menu not mounted yet" state caught by a frame only sometimes). So the **baselines hold only the `all` stream**.

**Using the baselines in later P5.02 steps**
- Step 1 (dead code): expect byte-identical — `LIFECYCLE_TRACE_DIR=<tmp> … npx playwright test zz-lifecycle-baseline`
  then `diff -r test/e2e/canvas/lifecycle-baselines <tmp>`.
- Steps 4+ (batched writes): run with `LIFECYCLE_BASELINE_DIR=test/e2e/canvas/lifecycle-baselines` as well.
  `compareTraces` passes only if the fresh trace is the baseline **with states removed** (same first and last state,
  nothing new, order kept) and prints the dropped states. Review those: dropping a store-only intermediate is the
  point of batching; dropping a state with a pie/panel animation class in it is a painted change.
- Step 11 fixes (NEW-2, NEW-4, …) change traces on purpose: re-record the affected baselines in the fix commit and
  update the assertions labelled NEW-2 (F34), NEW-4 (F35), NEW-10 (F37).

## Findings (numbered after P5.02a's NEW-1…NEW-8)

- **NEW-1, NEW-2, NEW-4 confirmed by reproduction.** Click-away's trace is identical to Escape's (F35). NEW-2 and NEW-4
  behave exactly as P5.02a describes (F34, F35 stage-2 test).
- **NEW-9 After NEW-2's Back, `justCompletedCarouselExit` stays true while the carousel stays open.** The stage-1
  Back raises the exit guard before the transition; because H-pieExit then takes the stage-swap row instead of
  closing, nothing lowers it (only H-cxDone's 300 ms timer does). Evidence: `F34_cancelBack.json`, the guard is set
  from the first Back until 300 ms after the carousel finally closes, across a whole stage-2 round trip (asserted in
  F34). While it is up, E-sel will not clear the target on a lost selection, E-cleanup is blocked, and H-click's exit
  guard returns early. Fixing NEW-2 (Back clearing the flag) removes this too. *Low on its own.*
- **NEW-10 Switching web with a pie open does not play the shrink; §4.9's first "must preserve" bullet is wrong.**
  Trace (`F37.json`): after the switch, selection → `[]`, target → null (E-closeAll), then `currentPieMenuData` →
  null while `isPieMenuRendered` stays true, then the menu is gone; the painted frames go straight from a steady pie
  in web A to no pie in web B. Mechanism (read at 46026ca): E-closeAll and E-rebuild run in the same effect flush;
  E-rebuild's closure still has the old target (`i-alpha`) but already has web B's `nodes`, finds no such node and
  takes its `setCurrentPieMenuData(null)` branch; the layer's mount gate (`isPieMenuRendered && hasPieMenuData`)
  unmounts PieMenu, so H-pieExit never runs and `isPieMenuRendered` is left true (the A-3 case, reached in normal
  use). So the P5.02 `GRAPH_CHANGED` event must reproduce "data null at once, rendered left true" to be trace-equal,
  or this becomes a deliberate change (the shrink §4.9 expected, or clearing `isPieMenuRendered`). Grant's call.
  Consequence of the stuck flag: E-vision does not clear the hover chip for that menu (as A-3 says).
- **NEW-11 T2 (retarget A→B while open) is not reachable with a mouse click.** A click on another node **adds** it to
  the selection (`components/canvas/input/pointerHandlers.js` toggles membership), so the pie closes on a two-node
  selection (`F6_secondClick.json`: `sel=[i-alpha,i-gamma]`, target null, shrink x8, multi-node panel enters). T2
  and A-2's one-render blip only arise from direct target writers (Wizard select, touch deferred tap, duplicate…),
  none of which a scenario here drives. The doc's "click another node" wording for T2 should change.
- Confirmed as documented, no surprise: T4/T5 (F33), T7 (F34), T9 (F35), T10 incl. "no exit guard on swap" (F36), and
  §4.7's asymmetric CUT between the node and abstraction panels (F35 node-panel test). With the node panel **off**
  (the default), the abstraction panel animates out on close; with it on, E-node cuts it.
- Tooling note, not an app bug: the frame-stream nondeterminism above. A future "painted-state" check needs a
  tolerance for the carousel-exit tail, or has to reason from the `all` stream as `compareTraces` does.
