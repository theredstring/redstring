## 1. How the reducer stays behaviour-exact: a commit loop

P5.02a §6.4 says: apply the event, then `reconcile()`, then `maybeFullReset()`. **The code doesn't run in that order**, so the reducer doesn't either (NEW-9).
- Today each lifecycle rule is a NodeCanvas effect. It re-runs when a dep changes, reads the values of *its* render, and its writes land in the *next* render.
- E-cleanup is declared before E-sel. In one flush it therefore judges its guard (`size==1 ∧ target`) on the target as it was **before** E-sel re-targets.

So `reducePie` does this:
1. It applies the event's own writes as commit 0.
2. It replays the lifecycle effects commit by commit until nothing changes (cap: 12 commits, then `console.error`).
   - An effect runs only if one of its deps changed from the previous commit (`Object.is`, as React compares deps).
   - It reads that commit's values, never another effect's writes from the same commit.
   - Writes merge in declaration order and the later one wins. A write equal to the current value is skipped, as the store setters skip it.
3. `patch` is the net change against the input state.

Replayed, in NodeCanvas declaration order:
- E-cxFrame (frame command only)
- E-closeReq
- E-promptStage
- E-decomposeFrame (frame)
- E-focus (frame)
- E-recompose (frame)
- E-return
- E-cleanup
- E-closeAll
- E-page
- E-colorPicker
- E-sel
- E-vision
- E-watchdog

E-rebuild and E-buttonsSync stay in NodeCanvas; they dispatch `PIE_DATA` / `PIE_BUTTONS`.

This is how every trigger rule in the brief falls out of the loop, without being special-cased:
- the watchdog arms when `isTransitioningPieMenu` rises and is cancelled when it falls;
- NEW-3's "exit guard lowered while already false re-runs nothing";
- E-cleanup's four triggers.

### Commands and the runner (step 3)

`dispatchPie(event, env)`:
1. Runs `reducePie(getState(), event, env)`.
2. Applies the patch in **one** `set` (it skips the set when the patch is empty).
3. Runs the commands in order.
4. Returns `{ patch, commands }`.

How each command is handled:
- **`after`**: a timer that dispatches its event with no env.
  - With a `key`, it replaces a pending timer of that key. Only the watchdog has a key.
  - Without a key, it is never cancelled. That matches today's guard timers (NEW-6).
- **`cancel`**: clears the timer with that key.
- **`frame`, `graph`, `local`**: go to the handler registered with `setPieCommandHandler(fn)`. It is exported, and also on the store. It returns an unregister function, which removes the handler only if it is still the current one.
- **With no handler registered:**
  - `graph` commands are **queued** and handed over in order when a handler registers, because a Swap must not be lost.
  - `frame` and `local` commands are **dropped**, because a late camera move or a late reset of NodeCanvas locals would act on a view that has moved on.
- **Test helpers:** `resetPieRunner()` clears all timers, the queue and the handler. `runPieCommands` is exported for tests.

`local` actions:
- `fullReset`: every NodeCanvas local that E-cleanup clears:
  - editingGroupId, tempGroupName, plusSign;
  - `selectionStart` and `selectionStartRef`;
  - drawingConnectionFrom;
  - the pie colour picker;
  - the carousel focused scale (1.2), dims and node;
  - the abstraction panel CUT.
- `closeAllPanels`: node, connection, abstraction and group panels `visible=false`.
- `closePieColorPicker`
- `clearCarouselFocus`: focused node and dims set to null.
- `carouselFocusPrototypeRequest {prototypeId}`

## 4. Where the doc and the code disagree (the code was followed)

- **NEW-9 (order).** §6.4 says "reconcile() then maybeFullReset()". The code runs E-cleanup before E-sel, on the same pre-E-sel snapshot.
  - Case where it matters: the watchdog fires with one node selected but no target (the target was cleared mid-transition).
    - Code: E-cleanup resets; E-sel re-targets A from the stale selection; the next commit clears it again.
    - Doc's order: A stays selected with its pie.
  - Handled by the commit loop. Test: "CURRENT BEHAVIOUR (order, NEW-9)".
- **NEW-12.** E-colorPicker closes the picker when there is **no data or no target**. Its deps are `hasPieMenuData` and the target. The doc's side rule says "target null" only.
  - So `PIE_DATA(null)` (node gone) and `PIE_EXITED` close the picker too.
  - A retarget A→B doesn't close it.
- **NEW-13.** `CAROUSEL_OPEN_DIRECT`'s "ignore while `!visible ∧ exiting`" guard exists in the context menu only. `handleNodePanelAbstraction` has none, hence `guard:false`.
  - That state is practically unreachable either way.
- **NEW-14.** The doc's `CAROUSEL_LEAVE` bundles the click guard, but these paths raise the click guard **without** a leave:
  - `carousel-delete`;
  - Swap's early returns (no instance / no focused prototype);
  - Expand with no prototype data.

  Expand's no-definition path raises it at click time, then clears the target 50 ms later. Hence the separate `CLICK_GUARD` event and `raiseClickGuard:false`.
- **NEW-15.** `onCarouselAnimationStateChange` writes its argument unconditionally. The doc has "if entering → visible". This is equivalent in practice, since the carousel clears its 200 ms timer on any state change. Implemented unconditional.
- **NEW-16.** `requestCarouselClose` checks `abstractionCarouselVisibleRef`, which an effect mirrors one commit late. The reducer reads the live store value. This only differs in the commit right after the carousel opens or closes.
- **NEW-17.** §4.9 lists `hoveredEdgeInfo` as local. It has been in the store since P3.06a.
- **§6.4 `CAROUSEL_TOUCH_CLOSE` "Commands: —".** The close branch does raise the click-guard timer, as `onCarouselClose` does.

## 6. What wiring steps 4–10 need to know

- **env.** `PIE_EXITED` needs `findNode` over the **current** hydrated nodes. Use a ref: the callback should become stable, which is also F-27's fix.
  - `CAROUSEL_EXITED` needs `activeGraphId` for the swap command.
- **Register one handler** early (layout effect on mount), via `setPieCommandHandler`, keeping its unregister function.
  - `graph applyCarouselSwap {swap, graphId}`: move H-cxDone's centre-preserving math (old and new `getNodeDimensions`, `updateNodeInstance(..., {finalize:true})`) into the handler.
  - `frame`: the reducer applies only the guards it can see. The handler must add the rest:
    - `focusOnSelect`: `FOCUS_ON_SELECT_ENABLED && focusOnSelectEnabled`, no `draggingNodeInfoRef`, `selectedInstanceIdsRef.size <= 1`;
    - `recompose`: no drag;
    - `carouselOpen` / `decomposeOpen`: node lookup.

    All go through `runFramingAfterCommit`, because commands run inside `dispatchPie`, before React commits.
  - `local`: the five actions in §2.
- **Return framing must move in step 4.** The reducer consumes `pendingCarouselReturnFocusId` in the same patch that hides the carousel. So once `CAROUSEL_EXITED` is wired, E-return can never see it.
  - Handle `frame returnFocus` in the handler, and delete E-return in the same step.
- **The carousel's callbacks become stable** (`() => dispatchPie(...)`). This removes NEW-3's exit-timer restart on a web change.
  - That is the one intended timing change (P5.02a §6.6, Q7). Call it out in the commit.
- **Double execution while effects remain (steps 4–5).** The reducer replays the effects, and the NodeCanvas effects will still run afterwards.
  - On a settled state every replayed rule is idempotent, so they converge on the same values.
  - Expect two watchdog timers (both harmless) and, with a `local` handler registered, a doubled `fullReset`.
  - If the step-0 traces diverge, a per-effect replay switch in `env` is a small addition. I did not add it, to keep env minimal.
- **Step 6.** `SELECTION_CHANGED` must follow every selection write. It is safe to dispatch without `ids` after a setter call, because E-sel is forced and idempotent.
  - `MARQUEE` must go wherever `setSelectionStart` is called.
  - The `fullReset` local handler must clear `selectionStart`; the reducer already clears `marqueeActive`.
- **Step 7.** `GRAPH_CHANGED` replaces both E-cleanup's graph trigger and E-closeAll. The reset's store fields land in the patch.
  - `resetNonce` is bumped as well, in case an effect-based local reset is preferred to the `local` command.
