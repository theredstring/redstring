## What changed

### 1. `imageCache.clearImage`
- If `protoId` is not an own key of `images`, the updater returns `state`. Zustand's `setState` then sees the same object (`Object.is`) and notifies nobody.
- The check is key **presence** (`hasOwnProperty`), not truthiness. A key that is present with an `undefined` value is still deleted, as before.
- When the key is present, nothing changes. The deferred `URL.revokeObjectURL` for `blob:` URLs is untouched.

### 2. `imageCache.setImage`
The updater returns `state` only when **all** of these hold:
- `failed[protoId]` is not set. A set flag always takes the write path, because clearing it is a change.
- `protoId` is already an own key of `images`.
- The new entry is "the same" as the stored one: either the identical reference, or both are objects with the same own enumerable keys and `Object.is`-equal values. For the real shape `{ thumbnailSrc, imageAspectRatio }` that means the same `thumbnailSrc` **and** the same ratio.

Everything else is written exactly as before, including a different blob URL, a changed ratio, an added or missing field, a non-object, or a new key with an `undefined` value.

**Callers.** `setImage` has one caller, `_processSingleImage` in `imageCache.js`. It always passes a freshly created blob URL, so this guard never fires on today's fetch path (NEW-5). The guard is for the S10b scenario and any future caller.

### 3. `graphStore.setSelectedEdgeIds`
- It still builds `new Set(edgeIds)` first, so throwing on a non-iterable is unchanged.
- It then compares with the current `selectedEdgeIds`: same size, and every id of the new Set present in the current one. On a match it returns **without calling `set`**. This is the same early-return shape `setInputMode` already uses.
- Duplicates, order and iterable type don't matter: an array, Set, Map key iterator, or `undefined`/`[]` for "empty" all compare correctly.
- If the current value isn't a Set, the write happens as before.
- The `console.log` is removed.
- **MCP bridge:** it does not serialise `selectedEdgeIds`. `BridgeClient.sendStoreToServer` calls `buildBridgeState` (`src/services/bridgeStateSerializer.js`), which contains no selection fields. No bridge changes were needed.

**What a no-op `set` cost before (now skipped).** `saveCoordinatorMiddleware`'s `enhancedSet`, graphStore ~1145:
1. It runs `countUserData(get())` twice, for the collapse tripwire.
2. It installs and clears the patch listener. A plain-object `set` produces no patches, so nothing is recorded to history.
3. It clears and re-arms `pendingNotification`, which calls `SaveCoordinator.onStateChange(state, {type:'unknown'})` via `setTimeout(0)`.
4. It resets `changeContext` synchronously.
5. Zustand's object-partial `set` always builds a new state object, so every subscriber's selector runs. The `selectedEdgeIds` selector got a fresh Set, which meant a NodeCanvas render.

**Caveat about item 4.** When we skip `set`, `changeContext` is not reset. So a caller that did `setChangeContext(...)` and then made `setSelectedEdgeIds` its **only** write would leak that context into the next write.
- I checked every caller: the three NodeCanvas sites (~6363, ~14464, ~18702, each right after `setSelectedEdgeId`, which does write), TypeList.jsx:261, and `toolResultApplier` (which never calls it). None of them does that.

### 4. `useCanvasTransform` settle
Both the settle timer and `flushSettle` now call `commitSettled()`.

**Skip condition.** `commitSettled` skips `setSettledPan`/`setSettledZoom` only when:
- the refs' `x`, `y` and `zoom` are `Object.is`-equal to what the settled state last committed (`lastSettledRef`), **and**
- the view has not been anywhere else since then (`movedSinceSettleRef`).

**Where movement is recorded.** `movedSinceSettleRef` is set in `applyTransform`. Every mutator calls `applyTransform`, and so do the direct ref writers:
- the keyboard/gamepad loop
- NodeCanvas's connection-draw edge-pan (~3458)
- useNodeDrag's edge auto-pan (~3081)

The two edge-pan writers also call `setPanOffset`.

**Unchanged:**
- `movingRef = false` and the label restore still run on every settle.
- When a commit happens, it is the same `setSettledPan({ ...panRef.current })` + `setSettledZoom(z)` as before.

I also dated the "143 ms" figure in the file header (F-63). The second mention, in the LABEL SUPPRESSION block, is untouched.

## New findings

- **NEW-1 (process). This worktree was created at `b5444cc`, 5 commits behind `main`, with no plan docs and an older `imageCache.js`/`graphStore.js`.**
  - Before doing any work, I fast-forwarded this branch to `main` (`34649b4`) with `git reset --keep main`. The branch had no commits of its own, and nothing on `main` was touched.
  - `git worktree list` shows the other agent worktrees also at `b5444cc`. **Orchestrator: check the other lanes' bases.**

- **NEW-2 (behaviour, NodeCanvas). The view-save effect has no retry of its own.**
  - The effect is at ~9859. It drops the save in two places:
    - at effect time, if `pinchRef.current.active`, `draggingNodeInfo` or `isAnimatingZoomRef.current` is set
    - at timer time (+300 ms), if `isPanningOrZooming`, dragging, or animating is set
  - After a drop, it only runs again when `panOffset`/`zoomLevel` identity or `draggingNodeInfo` changes.
  - Before P1.09, a no-op settle happened to act as a retry. Now only a settle after real movement does.
  - I walked the paths:
    - Wheel and trackpad clear `isPanningOrZooming` within 100 ms, so their clamp no-op settles never follow a dropped save.
    - A held-still pinch lifts with no glide, which means no mutation, so there is no settle today either.
    - Drag-pan held still for more than ~450 ms and then released: no mutation today either.
  - So the retry lost here needs a dropped save followed by **purely** no-op mutations, for example pushing against a clamp. That is rare.
  - **The pre-existing gap is the bigger issue:** after a held-still pinch or drag-pan release, the final camera isn't saved until the next move.
  - Fixing it needs a NodeCanvas change (Lane A, e.g. P3.10/P3.11). Re-arm the save on gesture end, or save from the refs when `isPanningOrZooming` drops, instead of relying on the settle identity. **Not done here, by scope.**

- **NEW-3 (harmless).** EdgeGlowIndicator's settle trim (`[paint, panOffset, zoomLevel]`) no longer runs on a zero-movement settle.
  - A zero-movement "gesture" repaints the same view, so it claims no slack.
  - Slack claimed by a geometry change is trimmed at the next real settle rather than an incidental no-op one.

- **NEW-4.** A no-op graphStore `set` isn't free. See the five middleware costs in §3. Any other action that commonly writes an unchanged value is worth the same guard, as long as nothing sets a change context right before it.

- **NEW-5.** `setImage`'s only caller always passes a new blob URL, so the `setImage` guard doesn't fire on the current fetch path.
  - The real-world no-ops come from `clearImage`: `SharedPanelContent.jsx:747` clears before re-queueing, whether or not anything is cached.
  - The other `clearImage` sources are `cancelThumbnailFetch` and `retryThumbnailFetch`.
  - For S10b to show 0 commits, the harness has to call `setImage` with the **already cached** entry, or an equal one.

- **NEW-6.** `test/store/graphStore.test.js` has 11 failures on `main` (`34649b4`). They are stale tests for an old API. Worth a card, or deleting.

3. **No manual Profiler before/after** (the card is pre-P0 OK). There was no browser in this session. Unit-level render and notification counts stand in for it.
