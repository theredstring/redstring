## What changed

**`src/utils/perf/renderProbe.js`** (new)
- `createRenderProbe({ enabled })` is the factory; tests use it. The module singleton `renderProbe` is what the app uses, and `onRenderProbe` is its stable `onRender`.
- `window.__renderProbe` exposes:
  - `enable()` and `disable()`. `disable()` also discards any running session.
  - `isEnabled()`
  - `start(label)`
  - `stop()`
  - `reset()`
  - `onRender`
- `stop()` returns plain JSON:
  `{ label, commits, totalMs, maxMs, wallMs, byId: { [id]: { commits, totalMs, maxMs, phases: { mount, update, 'nested-update' } } } }`
  - Milliseconds are rounded to µs.
  - `wallMs` is the time from `start()` to `stop()`, so commits per second can be computed.
- **When it records:** only while the probe is enabled *and* a session is running. It is enabled by `?probe=1` at load or by `enable()`. In any other state `onRender` returns after its first check.
- **Top-level `commits`:** the number of React commits in which any Profiler reported.
  - Calls are grouped by `commitTime`.
  - A second report from the same id under the same `commitTime` starts a new commit. This catches a synchronous follow-up commit that falls inside the timer's resolution.
- **Top-level ms:** each commit counts its largest `actualDuration`.
  - With nested Profilers (the plan's layers inside NodeCanvas), that is the outer one, which already includes the inner ones.
  - Sibling Profilers that commit together are under-counted at top level. Read those from `byId`.
- **Normal production builds:** the probe is *not* put on `window`, even with `?probe=1`.
  - The gate is `import.meta.env.DEV || MODE === 'profile'`, which Vite folds at build time.
  - React never calls `onRender` in those builds anyway. Leaving the probe off `window` makes a harness that points at the wrong build fail loudly (`__renderProbe` is undefined) instead of reporting 0 commits.
- **Misuse fails loudly:** `start()` throws while the probe is off, and `stop()` with no session returns `null`.

**`src/App.jsx`:** `<Profiler id="NodeCanvas" onRender={onRenderProbe}>` wraps `<NodeCanvas />`. That, plus the import, is the whole diff.

## New findings

**NEW-1. Profiler durations are quantized to 0.1 ms in the browser.** VERIFIED.
- Every duration observed was a multiple of 0.1 ms: Chrome coarsens `performance.now()` to 100 µs on pages that aren't cross-origin isolated.
- For NodeCanvas (multi-ms commits on real graphs) this doesn't matter.
- For small per-layer Profilers later (P3), the relative error gets large.
- Option for P0.04/P3: serve `preview:profile` cross-origin isolated (`Cross-Origin-Opener-Policy: same-origin` plus `Cross-Origin-Embedder-Policy: credentialless`, so Wikipedia images still load) to get 5 µs resolution. Not done here.

**NEW-2. Running `vite` dev from a worktree writes the main checkout's dep cache.** INFERRED from Vite's default `cacheDir` and the symlink setup. Not triggered: I avoided it.
- The worktree's `node_modules` is a symlink to the main checkout, and Vite's default `cacheDir` is `<root>/node_modules/.vite`.
- So a dev server started in a worktree rewrites the dep-optimizer cache that Grant's dev server on :4001 uses.
- For my dev-server check I used a scratch config with `cacheDir` in the scratchpad.
- **Relevant to P0.03:** a Playwright `webServer` that runs `vite` dev from a worktree should set `cacheDir` (e.g. from an env var). Builds and `vite preview` don't use that cache.

**NEW-3. StrictMode inflates durations but not commit counts.** VERIFIED. This refines F-28.
- jsdom: the same updates give 2 commits with or without `<StrictMode>`.
- Browser: the same darkMode ×2 interaction took 13.8 ms in dev and 3.4–4.6 ms in the profile build.
- So commit counts from the dev server are usable. Milliseconds must come from `build:profile`.

**NEW-4. Every root commit during a pan rendered NodeCanvas.** VERIFIED on a scratch graph.
- Probe commits equalled root commits exactly in all three pan runs: 126, 125, and 86 in an earlier run whose browser profile was reused.
- Each run lasted about 3.5 s of wall time: 60 pointer moves sent over CDP, then 1.5 s of settle.
- 126 commits for 60 moves plus momentum is consistent with F-01: pan commits NodeCanvas about once per frame. I did not derive a per-second rate, because the CDP round-trips stretch the drag.

**NEW-5. The normal production bundle still contains the probe module.** VERIFIED.
- About 1 KB of `renderProbe.js` ships, because App references `onRenderProbe`. The `window` install is compiled out.
- There is no runtime cost, because React never calls `onRender` there.
- Removing the module entirely would need a conditional import. Not worth it.

## Proposed DECISION: render-cause attribution

**D-16 (proposed). Attribute renders with a small dev-only helper built on the probe. React DevTools' "why did this render" is the manual fallback. why-did-you-render is rejected.** *Proposed (Claude), 2026-09-23.*

**The helper, in two parts:**
1. **Store-write attribution. No NodeCanvas edits.**
   - While a probe session runs, subscribe to `useGraphStore` (and `useImageCache` etc.).
   - Record which top-level keys changed on each write (`Object.is`), and attach the tally to the `stop()` result, e.g. `causes: { 'graphStore.graphs': 10, 'imageCache.images': 20 }`.
   - This is scriptable from Playwright, and it answers success criterion 3 and scenarios S10/S11 directly.
2. **`useRenderCause(id, namedValues)`.** A hook each new layer or host (P2/P3) calls with its handful of selector results and props.
   - It diffs them against the previous render and tallies the changed names into the probe session under that id.
   - It is dev and profile only, with the same gate as the probe.
   - NodeCanvas itself gets one call, holding only the values a P1 task is investigating. That call is Lane A work.

**Why:**
- It reports *named* causes ("`hoveredEdgeId`", "`graphStore.graphs`") as JSON inside the same `start/stop` session the harness already uses.
- It needs no dependency and doesn't change React or the JSX runtime.
- It also runs in the profile build, where milliseconds are taken.

**React DevTools "Record why each component rendered while profiling"**
- It needs no code, and it works in both the dev and profile builds. Use it for ad-hoc investigation.
- It is manual only, so a harness can't script it.
- For NodeCanvas it reports "Hook N changed" by index. The component has about 700 hook calls (F-40), so an index is hard to map back to code. Hook-name parsing through source maps helps, but is slow on a 19k-line file.

**`@welldone-software/why-did-you-render`: rejected.** Checked against the npm registry and the 8.0.3 tarball; it is not installed.
- **Version line:** the latest release (10.0.1) requires `react ^19`. React 18.3 needs the 8.x line (8.0.3, `react ^18`), which then has to be bumped when React goes to 19.
- **zustand 5:** it would work. v8 tracks `useSyncExternalStore` along with `useState`, `useReducer` and `useContext`, and zustand 5.0.3 calls `React.useSyncExternalStore` at call time, which WDYR patches. But it reports unnamed hook results.
- **Setup and cost:** it requires:
  - swapping the dev JSX runtime (`jsxImportSource: '@welldone-software/why-did-you-render'` in plugin-react)
  - a first-import `wdyr.js` in `main.jsx`
  - monkey-patching React

  Its README says it "significantly slows down React" and must never run in production. So it perturbs the renders we're measuring, and it can't run on the profile build.
- **Weak fit:** its strongest feature is props diffs on memoized components. NodeCanvas has no props. That only becomes relevant once the P3 layers exist, and helper part 2 covers it.
