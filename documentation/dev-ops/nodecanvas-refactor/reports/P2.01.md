## §4 Timing risk: Zustand vs batched `useState`

**The mechanism** (verified in `node_modules`):
- zustand 5's `useStore` is `React.useSyncExternalStore`.
- React 18.3's `forceStoreRerender` always schedules **SyncLane**, which flushes in a microtask.
- A `useState` update takes its lane from `window.event`. Discrete events (click, mousedown, keydown, pointerup, touchend) get SyncLane. Everything else gets **DefaultLane**, rendered later through the scheduler. "Everything else" includes:
  - `setTimeout`
  - `requestAnimationFrame`
  - promises
  - `animationend`
  - CustomEvents

So:
- Inside a discrete event, store writes and `useState` writes batch into one render, the same as today.
- **Outside one, a callback that writes the store and a `useState` renders twice.** The first render sees only the store half. Effects run between the two renders with a mixed state.
- Separately, `getState()` changes the moment `set` runs, while render-scope values lag until the next render.
- React doesn't double-invoke zustand updaters under StrictMode. Updaters must still be pure.

**Non-discrete writers that will mix the two during P2.02 and P2.03:**

**Effect chains that need care** (selection → pie → control panels):

1. **Graph Change Cleanup (~7646)** is the most dangerous.
   - Its deps are `[activeGraphId, abstractionCarouselVisible, justCompletedCarouselExit, isTransitioningPieMenu]`, so it runs on every carousel or transition flag change, not only on a graph change.
   - Unless its guards hold, it clears selection, preview, prompts, the pie and the carousel. The guards read `selectedInstanceIds` and `selectedNodeIdForPieMenu` from render scope, and those are deliberately not in the deps.
   - It is only correct if those values land in the **same render** as the flag that triggers it. A split render that flips a flag before the pie target or selection has landed can wipe the menu state.
   - **Keep it reading render-scope values, not `getState()`.** Move its trigger flags together with the pie target (P2.03), or `flushSync` the mixed callbacks.
2. **Close-all on graph change (~7852)**, deps `[activeGraphId]`.
   - Unconditionally clears selection, pie target, preview and group.
   - It runs right after #1 in the same commit, so #1's carousel guards never protect selection on a real graph change (NEW-3).
   - Harmless for the store, because clearing an empty Set is now skipped.
3. **Pie visibility effect (~13034).**
   - Deps: selection, `isTransitioningPieMenu`, `abstractionPrompt.visible`, carousel flags, `selectedNodeIdForPieMenu`, `selectionStart`.
   - After P2.02, selection renders first and the pie target lands in the effect's own later render. That is the same order as today for discrete events. Watch S6/S7 commit counts for the non-discrete writers in the table.
4. **Pie data effect (~13099)**: see the PieMenu row in the table.
5. **Control-panel effects (~7756 node, ~7783 connection, ~7803 edge pie, ~7834 group).**

   - After P2.02 both selections are zustand and in the same lane, which is better than today.
   - The node and connection effects call `setSelectedGroup(null)`, which becomes `setSelectedGroupId(null)` in P2.03.
6. **Identity re-triggers.** With Set equality, writing an equal selection no longer re-runs effects keyed on selection. I checked the ones that matter:

   Note that these refs update after commit, while `getState()` updates at `set`. A handler that sets and then reads will now see the new value.
