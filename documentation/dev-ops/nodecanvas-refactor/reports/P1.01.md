- **Status:** done (Lane A worktree agent, 2026-09-23)

## What changed
- `src/NodeCanvas.jsx`:
  - Deleted `const [panStart, _setPanStartState] = useState(...)`.
  - `setPanStart` now writes only `panStartRef` (it keeps the functional-updater form).
  - In the `handleMouseMove` drag-pan rAF, moved `setPanStart(...)` **out of** the `setPanOffset(prev => …)` updater. It now runs right after the call, guarded by the same `appliedDx !== 0 || appliedDy !== 0` test. This is safe because `setPanOffset` is `transform.setPan`, which runs the updater synchronously (`useCanvasTransform.js`, `setPan`), so `appliedDx` and `appliedDy` are final when it returns. Between the old and new positions nothing reads `panStartRef` (`applyTransform`, `scheduleSettle`, `onTransformChange`), and the rAF has already captured `ps`.
  - Updated the ref-mirroring comment so it no longer describes `panStart` as state.
- New `src/NodeCanvas.renderBudget.test.jsx`: the first render-budget regression test (see below).
- Pan maths, momentum and the pinch→one-finger handoff are untouched. `useCanvasTouch` still calls `setPanStart(...)` and `setPanStart(null)`, and those now write the ref only.

## Measurements (jsdom render-count check, stands in for S1 / S1t)
`src/NodeCanvas.renderBudget.test.jsx` wraps NodeCanvas in a React `<Profiler>` and counts every commit under it. It reuses the smoke test's harness: culling off at import, WorkspaceService and canvasWorker mocks, a hand-driven rAF queue, and canvas/SVG/rect stubs. Each case mounts and settles first, then:
- **Mouse (S1):** `mousedown` on `svg.canvas`, then 2 warm-up `mousemove`s, then 30 `mousemove`s (6 px each, with one rAF flush per move), then `mouseup`.
- **Touch (S1t):** the same shape, driven through `touchstart`/`touchmove`/`touchend` on `svg.canvas`, which goes through `useCanvasTouch` into the same `handleMouseMove` pan path.
- Each case also asserts that the content `<g>`'s `transform` attribute changed, which proves the pan path really ran in jsdom.

"Before" was measured with `git checkout HEAD -- src/NodeCanvas.jsx` (base 34649b4), after which the edited file was restored. There were 3 runs each, all identical.

| Scenario | Press | Warm-up (2 moves) | Steady (30 moves) |
|---|---|---|---|
| S1 mouse drag-pan, before | 1 | 4 | **60** |
| S1 mouse drag-pan, after | 1 | 2 | **0** |
| S1t touch pan, before | 1 | 4 | **60** |
| S1t touch pan, after | 1 | 2 | **0** |

The test asserts `steady === 0` for both cases, so a reintroduced per-frame commit fails it.

**Limits of the check:** jsdom measures commit *counts*, not milliseconds. Culling is off, so culling-growth commits are out of scope. The settle commit (`setSettledPan`, fired from a real `setTimeout` after the gesture) falls outside the measured window by design. The window only proves "no per-frame commits".

## New findings
- **NEW-1: drag-pan cost 2 commits per frame, not 1.** F-01 predicted about 60 renders/s from `panStart`. The measured rate was 2 per frame: one from `setPanStart`, and one from `setHasMouseMovedSinceDown(true)`, which `handleMouseMove` calls on *every* move past the threshold (X-01 dead state). Setting the same value normally bails out eagerly. But while another state update commits every frame, React's eager bailout (`fiber.lanes === NoLanes` on both fiber and alternate) never applies, so each same-value set scheduled its own render and commit.
  - Experiment: base minus only that setter gave 30/30 (1 per frame).
  - P1.01 alone gives 0/30, because once nothing else commits per frame the same-value set bails out eagerly.
  - Lesson for later cards: a same-value `setState` in a hot path is only free while nothing else commits. P1.02 deletes `hasMouseMovedSinceDown` outright.
