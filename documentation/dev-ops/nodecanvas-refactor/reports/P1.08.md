# P1.08 report: stable `nodes` identity; `hydratedNodes` reuses objects

**Status:** done (orchestrator).

## What changed
- **`nodes`** now returns the previous array when every element was reused, in the same order.
  - It already reused element objects; only the array was new every time.
  - That new array invalidated `nodeById`, `baseDimsById`, the routing memos and the label index on writes that changed nothing on the active graph.
- **Bug in the reuse check, found by the memo counter.** It compared `prev.thumbnailSrc === effectiveThumb`:
  - For a node without an image, the built object's `thumbnailSrc` is `undefined` (spread from a prototype without the key), while `effectiveThumb` is `null`.
  - So an image-less node was never reused. Every `nodes` recompute rebuilt all of them, and each one re-rendered its `<Node>`, including during drags. The code's own comment says that shouldn't happen.
  - Now compared as `(prev.thumbnailSrc || null)`.
- **`hydratedNodes`:** reuses an object when its instance, prototype and cache entry are the same objects as last time. That's exact, because Immer keeps untouched objects by reference. It keeps the previous array when nothing changed.
- NodeCanvas.jsx: 18,412 lines, unchanged. The comments in the region were condensed.

## Why `hydratedNodes` wasn't folded into `nodes`
They carry different data:
- **`nodes`:**
  - overrides `name` with the prototype's
  - fills `imageAspectRatio` from `semanticMetadata` when the image is missing
  - adds `imageLoading`/`imageMissing`
  - reuses objects by comparing a list of fields, so a field outside that list (for example `semanticMetadata` or `typeNodeId`) can be stale on a reused object
- **`hydratedNodes`:** none of that, and never stale.

Its consumers (the groups pass, `EdgeGlowIndicator`, Panel, `ForceSimulationModal`, the hitbox overlay) would see different, sometimes stale, values if it became `nodes`.
