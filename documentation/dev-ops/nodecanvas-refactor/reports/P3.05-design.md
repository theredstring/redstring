## 0. TL;DR

- **Where labels are placed today.** Labels are placed inside the render, one edge at a time, in paint order: z-slot ascending, then `visibleEdges` order within each slot.
  - A routed label (manhattan, clean or lombardi) dodges every rect currently in `placedLabelsRef`. That map holds this render's earlier edges and the **previous** solve's entries for everything else: later edges, culled edges, deleted edges and self-loops.
  - A per-edge signature (`pathD | name | fontSize | truncate | crossing generation`) decides whether an edge re-solves or reuses its entry.
  - A module-level 5 px / 1° deadband (`labelStabilization.js`) holds positions across re-solves.
  - Straight and curved (non-routed) labels do no dodging. They sit at the apex of the visible segment and register nothing.
- **Why a pure pass can reproduce this exactly.** Label placement is **independent of hover and edge selection**. It depends on node selection only through geometry (6 px). So a pure pass `computeLabelPlacements(inputs, prevCommitted)` can reproduce today's at-rest placement exactly, provided it:
  - iterates in the same order;
  - seeds its working map from the **previous committed result**, preserving Map insertion order (obstacle overlap is a float sum, so order matters);
  - treats the scattered `.clear()` calls as explicit *reset keys*.
- **What cannot be reproduced exactly.** Some transient, one-render states can't be reproduced exactly (§3.8). Every one of them is either DOM-owned by the drag, or converges to the same steady state that the pure pass produces immediately.
- **P3.06.** `ConnectionEdge` becomes a `React.memo` component fed by:
  - a per-edge **route** record, hover-independent and structurally shared;
  - a per-edge **placement** record (from P3.05);
  - two booleans, `isHovered` and `isSelected`;
  - one memoized **style** object;
  - one **stable handler** object (the `useLatestRef` pattern from P3.02/P3.04).

  Hover moves into `canvasUIStore`, and `EdgeLayer` (or `EdgeSlot`) subscribes to it itself.
- **P3.07.** Delete the element cache and the painter, and do it **before** P3.06 rather than after:
  - both are off by default;
  - both are structurally incompatible with a component `ConnectionEdge` (the painter throws on component elements, and the cache duplicates `React.memo`);
  - keeping them alive through P3.06 costs more than it could save.

## 1. How edges get rendered today

### 1.1 The edges IIFE (NodeCanvas ~10233–10452)

It runs inside `svg.canvas`'s content group, after `groupElements.regular` and the hitbox debug view. It is gated on `isViewReady`.

1. **Z-slicing** (~10239–10261):
   - `edgeZSlots = groupStructure.edgeZSlots`, built by `buildEdgeZSlotIndex` (`services/groupLayout.js:468`). It maps instanceId to a slot: a node-group member gets `depth+1` and its anchor gets `depth`; deepest wins.
   - `topEdgeSlot = max(shell depths) + 1`.
   - Each visible edge goes to `edgeZSlotFor(edge, edgeZSlots, topEdgeSlot)` (`groupLayout.js:504`). That is `min(topSlot, max(slot(src), slot(dst)))`, and self-loops always go to `topSlot`.
   - `edgesBySlot` is a Map of slot to an array **in `visibleEdges` order**.
   - `edgeZSlotOrder` is the ascending sorted union of the slots that have edges, the shell depths (`groupElements.backgroundsByDepth`) and the nested plain-group depths (`groupElements.nestedRegularByDepth`).
2. **Emission** (~10422): for each slot in ascending order, one `<React.Fragment key="edge-z-slot-N">` containing, in this order:
   1. `nestedRegularGroupsByDepth.get(slot)`
   2. that slot's edges: `bucket.map(edge => renderEdgeCached(edge, edgeRenderCtx, edgeGlobalCacheKey))`
   3. `nodeGroupShellsByDepth.get(slot)`
3. **`visibleEdges` order** is `edges` order, which is `activeGraph.edgeIds` order. `runCulling` (~2592) rebuilds `commitEdges` by filtering the current `edges` (~2822–2845). The disabled-culling branch hands over `edgesRef.current` itself.

**Render (dodge) order is therefore: slot ascending, then `graph.edgeIds` order within the slot.** The element order in the DOM is the same. The painter path (§1.9) solves in exactly the same order.

`renderConnectionEdge` is called only from `renderEdgeCached` (~10280 and ~10297). With the cache off, which is the default, `renderEdgeCached` is just `renderConnectionEdge(edge, ctx)`.

### 1.3 The label IIFE (1342–1982), step by step

1. `connectionFontSize = resolveEdgeLabelFontSize(textSettings, connectionLabelSize)` (1343).
2. **Initial position** (1344–1365):
   - Manhattan branch (1347–1358): chord midpoint, axis angle. **Dead in practice:** with `enableAutoRouting && manhattan`, `orthoRouting` is always non-null, so the routed branch below overwrites midX/midY/angle.
   - Otherwise `labelPlacementPath.apexX/apexY/labelAngle`: the apex of the *visible*, selection-aware segment. **This is the final position for straight and curved (non-routed) labels. There is no dodge.**
3. **`connectionName`** (1368–1379): the definition proto's name, else the type proto's name (including `base-connection-prototype`), else `'Connection'`.
4. **Straight truncation** (1397–1407): when `connectionLabelTruncate && !orthoRouting`, `truncateEdgeLabel(name, fs, hypot(visibleEndpoints) * LABEL_TRUNCATE_FILL)`. This is selection-dependent, because the visible segment shrinks 6 px at a selected end.
5. **Routed branch** (1418–1529), used for manhattan, clean and lombardi:
   - `labelSignature = \`${orthoRouting.pathD}|${connectionName}|${connectionFontSize}|${truncate?1:0}|${labelCrossingIndex?.generation ?? 0}\`` (1444). `pathD` is the **untrimmed** route, so hover never churns it.
   - **Hit** (1446–1457): `cached = placedLabelsRef.current.get(edge.id)` has `position`, `signature === labelSignature`, **and `!draggingNodeInfo`**. Then:
     - `displayName = cached.displayName ?? connectionName`;
     - the position is `stabilizeLabelPosition(id, cached.position…)`, which in practice returns `cached.position` (see §1.5);
     - **the entry is not rewritten.**
   - **Miss** (1458–1500):
     - Truncate against `routedLabelSpan(orthoRouting)`: the longest single run, or the visible arc length.
     - `placement = chooseRoutedLabelPlacement(orthoRouting, displayName, nodes, visibleNodeIds, baseDimsById, placedLabelsRef.current, fs, edge.id, selectedInstanceIds, labelObstacleOptions)`.
     - Then `stabilizeLabelPosition`.
     - Then **`placedLabelsRef.current.set(edge.id, { rect: labelBoundsFor(x, y, estimateTextWidth(displayName, fs), fs*1.1, angle), signature, displayName, position: {x,y,angle}, anchor: placement.anchor })`**. `anchor` is read by `useNodeDrag` to hold the label's position along the route mid-drag.
   - 1502–1527: a `window.__labelDebug` console diagnostic (render-phase `console.log`, off by default).
6. **Truncation report** (1541–1543): `labelTruncationRef.current.set(edge.id, displayName !== connectionName)`. It runs for every visible non-loop edge when names are on.
7. **Everything from here on is presentation only**; no placement decision is made:
   - `adjustedAngle = quantizeLabelAngle(flip(angle))` (1562);
   - glyph advances for lombardi arcs when `curveLabels` (1578);
   - `labelSpritesUsableNow = labelSpritesEnabled && !(truncate && draggingNodeInfo)` (1616);
   - `labelArcGlyphFrames(arc, pos, advances, { minBow: labelArcMinBow, rotationQuantum: spritesUsable ? 0 : curvedLabelQuantum })` (1626);
   - `glyphAttrs`, the `data-label-frame` token (1643–1650);
   - hit rect (1654);
   - colours (1657);
   - sprite peek/request (1699–1706);
   - glyph-sprite layers (1726–1784);
   - JSX in one of three forms: glyph sprites / whole-label sprite / `<text>` ring + label (1854–1981).

### 1.4 The dodge rule (`edgeLabelPlacement.js`)

`chooseRoutedLabelPlacement` (1321) dispatches as follows:
- `routing.arc` goes to `chooseArcLabelPlacement(arc, …, { ...options, range: routing.visibleRange })` (1089). This is lombardi with a visible bow.
- Anything else goes to `chooseOrthogonalLabelPlacement(labelPolylineOf(routing), …)` (861). This covers manhattan, clean, and a lombardi arc flattened below `lombardiMinBow`.

Both placers build their obstacles the same way (orthogonal ~875–882, arc ~1101–1108):

```js
const obstacles = (options.obstacles || getVisibleObstacleRects(...)).slice();
placedLabels.forEach((labelData, id) => { if (id !== edgeId && labelData?.rect) obstacles.push(labelData.rect); });
```

Consequences:
- **Every** entry in the map counts except the edge's own. That includes:
  - entries from previous renders for edges later in this render's order;
  - edges no longer visible (culled; never pruned);
  - deleted edges (until a clear);
  - self-loop entries.
- `options.obstacles` is always supplied (`labelObstacleOptions.obstacles`, or the frozen `EMPTY_OBSTACLES`, which is truthy). So the placer never reads the `nodes, visibleNodeIds, baseDimsById, selectedInstanceIds` arguments. **They are dead inputs.**
- Overlap is `overlapArea`, a **floating-point sum in obstacle order** (~407). Map insertion order therefore matters in principle, when a candidate ties within float noise. `Map.set` on an existing key keeps its position; `clear()` / `new Map()` resets it.
- Crossings are `countCrossingEdges(rect, options.segmentIndex, edgeId)`, which excludes the edge's own polyline.
- Candidates:
  - orthogonal: segments ≥ 24 px, along `[0.5, .42, .58, .34, .66, .25, .75]` × perpendicular `[0, ±0.6h, ±h]`;
  - arc: the `ARC_ALONG` ladder × `ARC_RADIAL_LADDER`.
- The winner is chosen by `betterPlacement`: overlap first, then crossings, then score.
- `estimateTextWidth` is `max(16, len * 0.55 * fs)`. It is pure and does not measure the DOM.

### 1.5 Stabilisation (`utils/canvas/labelStabilization.js`)

- A module-level `Map<edgeId, {lastX,lastY,lastAngle,timestamp}>`.
- `stabilizeLabelPosition(id, x, y, a)`:
  - no entry: store the input and return it;
  - otherwise, if the distance is < 5 px **and** the angular distance is < 1°: return the stored value (**hold**; the stored value is unchanged);
  - otherwise: store the input and return it. The lerp is gone, and so is the 15° snap.
- The timestamp is written and never read.
- It is only called for routed labels, on both hit and miss.
- **Invariant:** while an entry exists in `placedLabelsRef` with a matching signature, the stabiliser entry for that id is either absent (after a stab-only clear) or equal to `cached.position`. So on a hit, the output is always `cached.position`, and the stabiliser entry becomes `cached.position` if it was absent.
- The deadband is the hysteresis in F-72. A re-solve whose raw result is within 5 px / 1° of the old one keeps the old position, **and registers its rect at the held position.** Later labels dodge that rect.

### 1.6 Self-loops (`SelfLoopEdge.jsx`)

- A real component that renders **during reconciliation**, so after the whole NodeCanvas render body and after every `renderConnectionEdge` call of that render.
- Subscribes to five store fields itself (27–31): darkMode and four label settings.
- Label:
  - positioned at the loop apex, angle 0;
  - truncated against `loop.radius * 2 * FILL` (196);
  - writes `labelTruncationRef` (203);
  - writes `placedLabelsRef.set(id, { rect, position })`, with **no signature and no anchor** (207–214).
- **Consequence:** self-loop rects are never dodged by routed labels in the render that writes them. Only a later re-solve sees them, and then only if no clear happened in between.
- Its ring is gated on `labelColors.outerStroke` alone, not on `labelHaloEnabled && labelRingEnabled` as regular edges are. Keep this (it's behaviour).
- Selection click uses `selectedEdgeIds` and `storeActions` directly: no nearest-edge pick and no haptic, unlike regular edges.

### 1.7 Truncation

| Case | Measured against | When |
|---|---|---|
| straight or curved | chord of `visibleEndpoints` × 0.85 | every render |
| routed | `routedLabelSpan(orthoRouting)` × 0.85 | only on a miss; a hit reuses `cached.displayName` |
| self-loop | loop diameter × 0.85 | every render |

Measurement goes through `textMeasurement.js`:
- `truncateEdgeLabel` calls `edgeLabelGlyphAdvances`, which returns raw em buckets **until `document.fonts.check('bold Npx EmOne')` is true**, and after that normalises to a Pretext measurement.
- `ellipsisWidth` caches the first answer per font size. `initTextMeasurement` clears that cache on `fonts.ready`.

So truncation has one **hidden environmental input**: font-load state. It is not DOM layout, but it is not a React input either (§3.8, X3).

**One-render lag, more precisely.** The P3.03 card calls it a one-render lag. In fact `labelCrossingIndex`, `lombardiTangents` and `cleanLaneOffsets` read `anchorPositionUpdatesRef` when they recompute, and **none of them has the anchors as a dependency**. So they keep whatever anchors existed at their last recompute, which can be arbitrarily old, until `nodes`, `edges`, dims or settings change.
- At mount the ref is empty during the first render's memos, so these memos use the stored instance box.
- The anchor flush (~3081) writes the store if the stored and rendered anchors differ by more than 1 px, which recomputes the memos with the real anchors.
- If they agree within 1 px, the memos keep instance **dims**, which are not the pill dims.

The renderer, meanwhile, routes with current-frame anchors. **P3.05 must consume these same objects unchanged.** Fixing the lag is a separate, Grant-reviewed step (§5, step 7).

### 1.10 Every event that resets label state

The label state has two parts: the **P** map (`placedLabelsRef`, placements) and the **S** map (the module stabiliser). These events clear one or both.

| Where (~line) | Trigger | Clears | Timing |
|---|---|---|---|
| NodeCanvas 855–857 | `activeGraphId` change | S | effect, after the render |
| `resetConnectionLabelCache` 1637 | callers: auto-layout, snap-to-grid, condense, bring-into-bounds | P + S | synchronous, called from handlers |
| 1970–1978 | `draggingNodeInfo` goes truthy then null (drop) | P | effect, after the drop render |
| 3491–3494 | `enableAutoRouting, routingStyle, manhattanBends, cleanLaneSpacing, lombardiCurvature, showConnectionNames, connectionLabelSize, connectionLabelTruncate, textSettings.fontSize` | P + S | effect |
| 3526–3527 | `document.fonts.ready` (then `labelFontVersion++`) | P + S | promise |
| 3570–3573 | `connectionNameSignature` | P + S | effect |
| 9791 | auto-layout `runWhenFree` | S | handler |
| `useNodeDrag` 1895 | every drag frame that moves something: `placedLabelsRef.current = new Map()` (**replaces the object**) | P | per frame |
| `useNodeDrag` 1303 | per edge, in the routed per-frame path: `placedLabelsRef.current.delete(edgeId)` | P (one edge) | per frame |

The effect-based clears land **after** the render that needed them, and nothing forces another render. So today, after a routing-style switch:
1. render N solves with stale rects from the old style and the old deadband;
2. the clear runs;
3. the *next* render, whenever it happens for any reason, solves from empty.

The label DOM can show the render-N transient indefinitely. This is the root of F-72.

## 2. Canonical semantics: what "today's at-rest placement" means

For a fresh mount:
1. The first renders draw no edges, because `visibleEdges` starts empty.
2. The mount-time effects (§1.10: routing-config and name-signature) clear P and S after the first commit.
3. The first render that draws edges (after `runCulling` publishes `visibleEdges`) therefore solves **from an empty P and an empty S**.

`NodeCanvas.labelSnapshot.test.jsx` "at rest" captures exactly this pass (culling disabled). In the app, culling grows the visible set in steps. Each newly visible edge solves on its first appearance, against P holding everything solved before it.

Formally, one render's label pass over `order = [e1..en]` (paint order, §1.1), with P₀ and S₀ as they stand at render start:

```
W := copy of P₀ (same insertion order)       S := copy of S₀
for e in order, e not a self-loop, showConnectionNames:
  if e has no route (straight/curved):
      pos := apex(labelPlacementPath(visibleEndpoints))   // no W, no S
      name := truncate ? truncStraight(name, chord(visibleEndpoints)) : name
  else:
      sig := pathD|name|fs|trunc|gen
      c := W.get(e)
      if c && c.position && c.signature == sig && !dragging:
          name := c.displayName ?? name; pos := c.position; S[e] ??= pos
      else:
          name := truncate ? truncRouted(name, routedLabelSpan) : name
          raw := chooseRouted(route, name, obstacles ∪ {W[k].rect | k≠e}, index, fs, e)
          pos := stab(S, e, raw)                              // 5px/1° hold, else adopt
          W.set(e, {rect: bounds(pos, name), signature: sig, displayName: name, position: pos, anchor: raw.anchor})
  truncated[e] := name !== fullName
for e in order, e a self-loop, showConnectionNames:        // after all others (child reconciliation)
  W.set(e, {rect: loopRect, position: loopApex}); truncated[e] := …
P₁ := W ; S₁ := S
```

Then apply whichever resets fire between this render and the next (§1.10). **The pass is deterministic given (inputs, P₀, S₀).** Everything path-dependent about today's behaviour lives in P₀ and S₀.

## 4. Proposal 2: P3.06, a memoized `ConnectionEdge`

### 4.1 Tree

```
<EdgeLayer ...stable props>          // one component; renders the whole z-slot interleave
  for slot in edgeZSlotOrder:
    <Fragment key=edge-z-slot-N>
      {nestedRegularByDepth.get(slot)}   // memoized elements from P3.04 (stable identity)
      <EdgeSlot slot=N edges={bucket} …/>  // subscribes to hover + edge selection
      {backgroundsByDepth.get(slot)}
```

- Components add no DOM, so `svg.canvas` markup stays byte-identical.
- The **buckets** are memoized in `EdgeLayer` on `(visibleEdges, edgeZSlots, topEdgeSlot)`, so an `EdgeSlot`'s `edges` prop is stable.
- `EdgeSlot` maps `edges` to `<ConnectionEdge key=edge.id …/>`, or to `<SelfLoopEdge …/>` for loops.
- **Why `EdgeSlot` rather than subscribing in each `ConnectionEdge`:** a per-edge `useCanvasUIStore(s => s.hoveredEdgeId === id)` is also valid, because Zustand selector equality means only 2 edges re-render. It costs one subscription per edge, though, and every store write fires all the selectors. With a few hundred edges either is fine. Prefer per-edge selectors: they're simplest, and they make "hover re-renders exactly the old and new edge" true by construction. Keep `EdgeSlot` as the bucket or order holder only.

## 5. Proposal 3: P3.07, delete the cache and painter (recommended, and do it first)

**Recommendation:** delete both, *before* P3.06. Record this as an amendment to D-06, which currently says "revisit after P3.06, default retire".

**Why:**
1. They are off by default (`window.__edgeCache`, `window.__edgePainter`), so deleting them is zero behaviour change for users.
2. A component `ConnectionEdge` makes both obsolete by construction:
   - the painter consumes element trees from a plain function and **throws on component elements** (`paintElementTree.js` ~214);
   - the cache is a hand-rolled `React.memo` whose key misses on select, settle and drag (F-23), and whose hits corrupt the dodge order (§1.9). P3.05 fixes the latter anyway.
3. The painter changes event semantics (native `addEventListener`, ~153). It has to stand down for drags and repaint the whole subtree after them. It also adds a dependency-less `useLayoutEffect` that runs after every commit (4225).
4. "Measure first" (the card) can be satisfied cheaply before deleting. On chambers and stress, run S7-lombardi, S7-manhattan and S8 with `window.__edgeCache = window.__edgePainter = true` against off (profile build, 3 runs each), and record the result in METRICS. Keep a scoped version only if the painter saves more than about 20% of edge time on a scenario P3.06 won't already fix. Given §4.7, the only candidates are settled zoom and sprite landing, which are all-edge re-renders even after P3.06. If those numbers are bad, the right lever is P3.10 (viewport store) plus per-edge sprite subscriptions, not a parallel renderer.

**What to delete:**

In NodeCanvas:
- import `paintEdgeList` (168);
- `edgeElementCacheRef` and its comment block (4168–4186);
- the painter refs and `registerEdgeSlot` (4188–4212);
- `edgeCacheStatsRef` and the `window.__edgeCacheStats` effect (4214–4220);
