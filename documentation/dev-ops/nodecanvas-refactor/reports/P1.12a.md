## The answer to F-21: why selection is a dependency
Selection changes the geometry the labels are solved against:
- **`getNodeHitbox(node, dims, isSelected)`** adds 6 px on every side of a selected node: the selection stroke (`nodeHitbox.js`).
- **The drawn connection** ends at that larger box, so selecting a node pulls its connections' visible ends back by up to 6 px.
- **`labelCrossingIndex`'s `occluderFor`** trims each indexed polyline at the same selection-aware hitbox, so that "a label may only dodge what is actually drawn". A selection changes the polylines of every connection into the selected node, rebuilds the index and bumps its `generation`. `generation` is part of every label's cache signature, so all routed labels re-solve.
- **`labelObstacleOptions`** passes `selectedInstanceIds` to `getVisibleObstacleRects`, which grows the selected node's obstacle box the same way.

So the dependency is real, but small: 6 px at one end of the selected node's own connections.

## Two things the experiments turned up
**1. Label placement is path-dependent.** A pure no-op write (the `edges` Map replaced by an identical copy) re-solves every label, and some land somewhere else:

| Style | Labels moved by the 1st no-op re-solve | By the 2nd |
|---|---|---|
| manhattan | 2 of 16 | 0 |
| clean | 5 of 16 | 1 |
| lombardi | 0 | 0 |

The placement has hysteresis (`labelStabilization`), and the first solve after mount has nothing to be sticky against. In the app, any write to any edge anywhere in the universe replaces `edges` (F-07), so today labels can shift on an unrelated edit.

**2. What selecting the hub moves** (current code, from the snapshots):

| Style | Labels moved | Why |
|---|---|---|
| straight | 5 (1 when selecting the leaf) | the label sits on the drawn line, which is 6 px shorter at the selected end. Not a routed style: no crossing index |
| manhattan | 2 (the same 2 when selecting the leaf) | only the path-dependence above: selection doesn't change a manhattan polyline enough to matter, but the re-solve reshuffles |
| clean | 7 (5 when selecting the leaf) | 5 from path-dependence, 2 (`l-long`, `l-leads`) from the 6 px geometry |
| lombardi | 1 (0 when selecting the leaf) | the 6 px geometry; one stroke's `d` changes too |

## Variants measured
The variants were run in jsdom, mocking internals: `labelExplore3`. Solves are counted at `chooseRoutedLabelPlacement`.

| Variant | Change | Re-solves on a no-op write | Re-solves on select (manhattan / clean / lombardi) |
|---|---|---|---|
| V0 | today | 16 | 16 / 16 / 16 |
| V1 | don't rebuild or bump `generation` when the polylines are identical | 0 | 0 / 16 / 16 |
| V2 | V1, plus `occluderFor` ignores selection | 0 | 0 / 0 / 0 (1 for the lombardi hub) |
| V3 | V2, plus obstacles ignore selection | 0 | same as V2 |

- V1–V3 leave the at-rest labels identical to V0 in every style.
- V3 adds nothing to V2: obstacle identity isn't part of the label signature, so the obstacle half of the selection dependency never re-solves anything on its own.
- The cost of V2: while a node is selected, the crossing index treats its connections as reaching up to 6 px further than drawn. In this fixture, placement doesn't notice. (The 2 clean labels that V0 moves on select stay put, which is the point.)

## Recommendation for P1.12b
- **V1 + V2** (V3 unnecessary):
  - Skip rebuilding the crossing index when its polylines are unchanged.
  - Trim against the unselected hitbox in `occluderFor`.
  - Drop `selectedInstanceIds` from `labelCrossingIndex`'s dependencies. Keep it on `labelObstacleOptions` or not; it doesn't matter.
- **Open question, Grant's call:** with this fix, selecting a node no longer reshuffles labels. Today selecting reshuffles 1–7 labels, most of them on connections that didn't change, because every re-solve does. The "at rest" snapshots stay identical. The "selected" snapshots change by design: each "labels that moved" list becomes empty. The card says "don't change how labels are placed". The algorithm is unchanged, but the visible behaviour on select is not, so this needs an OK before P1.12b lands.
- **Measuring it:** S7 (select a node, labels on). Check `perf:canvas -- --explain S7`, and label solves via `window.__edgePerf`.
